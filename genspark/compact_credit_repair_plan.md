## اعتماد GO الحالي — استعادة 2026-09-10

هذا القسم هو المرجع الحالي ويتقدم على تفاصيل T00–T12 المؤرشفة أدناه، خصوصاً سياسة الست قراءات وحجب الصيانة القديمين.
المالك اعتمد تعديل الجسر والمحرك معاً، ثم أكد الاستثناء الآتي وطلب push-per-chunk لمقاومة resets.
الأساس الحالي `main@eb525bf`؛ تطبيق Antigravity مدموج بالفعل في PR #6 ولا يُعاد تنفيذه.

### الاستثناء الحاسم: COMPLETED للصيانة ليس اكتمال مهمة المستخدم

1. يرسل `/compact` مرة واحدة عبر مسار الشات وينتظر نهاية المحاولة باستخدام مراقبة مشتركة محدودة بمهلة وقابلة للإلغاء، بدلاً من حلقة التحقق الخاصة ذات الست قراءات.
2. اكتمال الصيانة ضوء أخضر داخلي فقط: لا return نهائي للمهمة، لا بطاقة اكتمال للمستخدم، ولا تنزيل ملفات صيانة. ينشر المشروع ويعرض كارت المتابعة الحية كما في المسار العادي.
3. يستمر فوراً بإرسال برومبت الاستئناف الطبيعي الأصلي مرة واحدة على نفس المشروع الحالي الذي خضع للصيانة، باستخدام التاريخ والجلسة الحاليين، ثم يراقب الرد الحقيقي حتى نهايته.
4. لا قيود صيانة إضافية بعد اكتمالها؛ لا اشتراط لملخص typed جديد بوصفه بوابة ثانية. تظل حماية الإلغاء وأخطاء النقل/الصلاحيات وعدم تداخل إرسال جديد مع توليد قائم هي الحماية الطبيعية.

### بقية النطاق المعتمد

- إزالة حلقة `COMPACT_VERIFY_READS=6` الخاصة واستبدالها بمراقبة نهاية مشتركة. نهاية الشبكة وحدها ليست إثباتاً للنهاية؛ أدلة FINISHED تخص المشروع/الجلسة/محاولة الطلب الحالية، لا حدثاً قديماً.
- إلغاء الحجب الدائم بسبب `COMPACT_BLOCKED` و`bypass_ready=false` القديم. يبقى تأجيل الصيانة لمنع تكرار الضغط، ولا تُمسح ملفات المستخدم أو manifest جماعياً. عدم وضوح الجاهزية يعطي نتيجة مؤقتة قابلة للتشخيص لا حجب صيانة دائم.
- إزالة جميع مقاطعات الرصيد النصية داخل SSE وفي فحص المحرك النهائي. تظل إشارات المنصة المهيكلة الصحيحة الحالية سبباً لنفاد الرصيد والتبديل القائم.
- إصلاح مساري `CREDIT_UNCONFIRMED` الأولي وأثناء polling: استمرار المراقبة بلا إعادة إرسال/تبديل، داخل مهلة الطلب القائمة دون إعادة ضبطها. لا يتحول النص الجزئي عند timeout إلى COMPLETED.
- حفظ الـpayload الفعلي بعد إعادة قراءة المحرك للسجل، لا الاكتفاء بتنظيف قائمة محلية يتجاهلها المحرك.
- الإبقاء على fallback الحفظ السحابي `allow_non_fast=True`، وعدم الخلط بين metadata وبين backup ملفات.

### الثوابت

`duration <= COMPACT_TRIGGER_SECONDS` وعتبة 180 وقياس المدة الحالي؛ manifest schema v1؛ عقد P18؛ الإلغاء؛ واجهة send_chat الثلاثية؛ أولوية GitHub الحالية؛ صفر archive/snapshot/diff/scan/upload في effective fast mode. Qwen وملفات anchor خارج النطاق. لا تجربة Genspark/Telegram حية أو merge أو deployment ضمن هذه الدفعة.

## 2. الهدف والنطاق الثابت

### الأهداف

- قبول الضغط الحقيقي وتثبيت التاريخ والجلسة الصحيحين للطلب التالي.
- عدم تحويل فشل صيانة اختياري إلى حجب دائم للطلبات العادية.
- عدم وقف متابعة توليد نشط بسبب رابط تسعير أو كلام عن الرصيد.
- استمرار نفاد الرصيد **المؤكد** في مسار الحفظ السحابي والتبديل القائم.
- عدم إرسال البرومبت مرتين أو الإعلان عن اكتمال غير مثبت.

### ثوابت لا تتغير

- `schema_version: 1`؛ أي metadata جديدة اختيارية ومتوافقة مع المانفيست القديم.
- `duration <= COMPACT_TRIGGER_SECONDS` وعتبة 180 وطريقة قياس المدة الحالية بلا إعادة تصميم.
- الضغط على الحساب المستلِم قبل الاستكمال؛ وبعد اكتمال العمل يؤجَّل إلى طلب المستخدم التالي.
- الوضع السريع الفعلي: صفر تنزيل أرشيف أو snapshot أو diff أو scan للملفات؛ checkpoint بيانات سحابي فقط. لا تعديل لأولوية GitHub الحالية.
- أزرار المعاينة والإلغاء، polling تيليجرام، تحرير الحسابات، ونطاق أسرار الحسابات بلا تغيير غير لازم.
- عقد P18: التوقف عند تغيّر مؤشرات النشاط يظل كما هو؛ الخطة لا تلغيه بحجة استمرار المراقبة.

## 3. التصميم المقترح وقواعد اتخاذ القرار

### 3.1 أدلة مرتبطة بالعملية لا بالمشروع عمومًا

تجميع metadata داخل cfg الخاص بالطلب، تشمل مشروع الطلب، الجلسة، علامة محاولة محلية، معرّفات الرسائل المعروفة، وحدث نهاية مرصود أثناء اتصال هذه المحاولة. تُصفّر قبل كل send وتُلغى بعد الاستخدام؛ لا state عام في الموديول.

لا ننسب chat_session_id إلى حدث ملخص لا يحتويه؛ مصدر الربط هو سياق الطلب ثم readback موثوق. بعد fork، يعاد الربط بالمشروع الفعلي؛ لا تنتقل نهاية مشروع قديم إلى مشروع جديد.

دليل `FINISHED` وحده لا يكفي: يُطابق المحاولة الحالية ويُجمع مع تاريخ مقروء وجلسة معلومة وعدم وجود توليد أحدث نشط. بعد restart لا يُعاد استخدام حدث SSE قديم؛ يجب جلب جاهزية حالية. إذا لم تتوفر metadata الموثوقة من مسار API، لا تُختلق من نص Nuxt الذي أسقطها.

### 3.2 إثبات الضغط

- قبول ملخص user المهيكل المرصود مع الحفاظ على توافق الملخص assistant القديم، دون قبول أي نص يقول إنه ملخص.
- العلامة boolean true، محتوى غير فارغ، بصمة حديثة مقارنة بالـbaseline، ومشروع/جلسة موثقان.
- قص التاريخ بدءًا من آخر ملخص صالح، لا الاقتصار على رد assistant الفارغ.
- توحيد شروط الاختيار والتثبيت في الجسر والمحرك حتى لا يقبل أحدهما ما يرفضه الآخر.
- لا تعني المدة أو HTTP 200 أو النص `/compact` وحدها نجاح الضغط.
- الإبقاء أولًا على نافذة التحقق المحدودة القائمة: 6 قراءات مع انتظار قابل للإلغاء؛ لا زيادتها عشوائيًا لأن زمن طلب SSE ليس زمن readback.

### 3.3 فصل الصيانة عن إرسال العمل

الأسماء التالية حالات تصميمية وليست وعدًا بإضافة جميعها كحالات عامة جديدة:

| الحالة الملاحظة | القرار |
|---|---|
| ضغط جديد موثّق + تاريخ/جلسة صالحان + لا توليد نشط | تثبيت السياق ثم إرسال البرومبت المنتظر |
| تعذر إثبات الضغط لكن المشروع الحالي جاهز بدليل موثوق | تأجيل الصيانة وإرسال العمل بالتاريخ الحالي، دون تسمية ذلك ضغطًا ناجحًا |
| توليد ما زال نشطًا | انتظار قابل للإلغاء ضمن الميزانية القائمة؛ لا إرسال متداخل ولا تكرار compact |
| تاريخ/جلسة غير مقروءين أو دليل قديم/متناقض | رفض مؤقت بسبب واضح وإعادة التقييم عند الطلب التالي؛ ليس حجبًا دائمًا محفوظًا |
| نفاد رصيد مهيكل حالي | مسار النفاد والحفظ/التدوير القائم |
| رفض صلاحية أو انتهاء جلسة | الحالة القائمة المناسبة، لا التحايل عليها بالتجاوز |
| إلغاء المستخدم | التوقف دون إرسال أو تدوير أو انتظار إضافي |

`deferred=true` تعني لا تعِد الصيانة الآن. `bypass_ready=false` القديم قرينة تاريخية وليس تصريحًا دائمًا بمنع العمل. لا نحذفه عميانيًا: يعاد تقييم الجاهزية الحية، ثم تحديث metadata عند نجاح القراءة. المانفيست السليم القديم بلا حقول compact يبقى صالحًا.

فشل حفظ الحالة لا يُعرض كنجاح حفظ. لا نخفّض ضمانات الحفظ القائمة في هذه الجولة: يرجع سبب تخزين قابل للتشخيص دون تحويله إلى قفل دائم أو الادعاء بإرسال لم يحدث. معالجة الكتابة المعطوبة شرط لنجاح مسار يحتاج حفظًا موثوقًا.

### 3.4 فصل الاشتباه النصي عن نفاد الرصيد

- نص التسعير في assistant/user/tool أو ملخص compact لا يوقف SSE ولا ينشئ نفادًا مؤكدًا.
- إشارة منصة مهيكلة صحيحة، مرتبطة بالدور/الحدث والطلب الحالي، تظل ذات أولوية لمسار النفاد القائم؛ لا تختلط بJSON مقتبس داخل content.
- عند sentinel قديم أو انقطاع البث، تُجلب الرسالة الحالية ويتابع البوت **نفس المشروع** دون إعادة البرومبت.
- داخل polling، الاشتباه بلا إثبات لا يخرج قبل بوابة النشاط. النشاط أو تغير المحتوى يعني استمرار المراقبة، لا انتهاء المهمة.
- اكتمال رد يتكلم عن الرصيد يُقبل فقط عند إثبات نهايته وهويته؛ لا يكفي أن يكون النص موجودًا.
- الانتظار محدود بـ`session_timeout` القائم، ولا يعاد ضبط الساعة كل مرة يظهر فيها الاشتباه. عند انتهاء الميزانية يعود فشل/عدم تأكد واضح مع آخر نص، بلا تدوير وبلا COMPLETED زائف.
- يُمنع تطبيق fallback «يوجد نص إذًا COMPLETED» على مسار الاشتباه غير المحسوم. هذا تعديل ضيق، وليس إعادة تصميم عامة لكل حالات timeout.
- الإلغاء وعقد P18 يظلان نافذين. إذا أوقف P18 المتابعة، لا يُحوَّل الاشتباه إلى تصريح بتجاهل ذلك العقد أو نجاح زائف.

### 3.5 منع تكرار إرسال العمل

اختبارات worker تثبت إرسالًا واحدًا لكل طلب داخل دورة تنفيذ معلومة. بعد reset في اللحظة بين إرسال الشبكة وحفظ النتيجة، لا يوجد ضمان exactly-once موزع بلا دعم من السيرفر.

القاعدة: مراجعة history ومعرّفات الرسائل والمحاولة قبل إعادة الإرسال. إذا تعذر حسم هل وصل البرومبت، فلا إعادة تلقائية عمياء؛ تُعلن الحالة غير المحسومة. الاستفادة من `client_message_id` إن أمكن إثبات دلالته، دون افتراض أن المنصة توفر idempotency غير موثقة.

## 5. مصفوفة اختبارات القبول الإلزامية

### Compact وهوية الجلسة

- C01: شكل HAR الأول: user summary، assistant فارغ، FINISHED.
- C02: شكل HAR الثاني بالقيم البنيوية نفسها وحجم محتوى مختلف.
- C03: توافق assistant summary القديم مع typed marker.
- C04: ملخص قديم، نص يدّعي التلخيص، marker نصي بدل boolean، محتوى فارغ: لا نجاح ضغط.
- C05: FINISHED قديم أو من مشروع مختلف، بما فيه نفس session ID: لا قبول.
- C06: الجلسة مفقودة، تغيّرت بين قراءتين، أو readback أقدم من الطلب: إعادة تحقق محدودة/تأجيل آمن.
- C07: Nuxt fallback الذي يفقد metadata لا يصنع إثباتًا؛ اختبار adapter دون استيراد البوت أو تسجيل الأسرار.
- C08: payload الفعلي التالي في كلا مساري الموديل يدعم user summary، session الصحيح، ولا يُرجع تاريخ ما قبل الضغط.

### الجاهزية والاستئناف

- R01: تعذر الضغط + جاهزية مثبتة: البرومبت الأصلي مرة واحدة.
- R02: الحالة نفسها على الحساب المستلِم: برومبت الاستكمال مرة واحدة.
- R03: مانفيست قديم `deferred=true,bypass_ready=false` ثم مشروع جاهز: استئناف بدون compact جديد.
- R04: active ثم inactive موثوق ضمن المهلة: انتظار ثم إرسال، لا تداخل توليد.
- R05: missing session، 401/403، fetch failure، pending بلا نهاية: لا إرسال غير آمن؛ سبب مميز وإعادة تقييم لاحقة.
- R06: فشل حفظ deferral لا يدّعي حفظًا؛ لا يحوّل نجاح العمل السابق إلى نفاد رصيد.
- R07: restart قبل الصيانة/بعدها/قبل send، وفشل الشبكة بعد send: لا إعادة عمياء لطلب قد وصل.
- R08: known distinct session، نفس الجلسة، same session/different project: لا تسرّب readiness أو suppression عبر المشاريع.

### الرصيد والمتابعة

- S01: pricing URL في message_result وسط توليد assistant مع نشاط قائم: يستهلك الأحداث التالية ولا ينهي المهمة.
- S02: العبارة نفسها داخل user/tool/compact summary أو كود مقتبس: لا exhaustion.
- S03: لاحقًا تصل typed ACTION_CREDIT_EXHAUSTED أو balance_drained أو quota flag: تأكيد ثم مسار النفاد القائم.
- S04: metadata قديمة أو من turn سابق لا تسمّم الرد الحالي؛ JSON مقتبس ليس typed signal.
- S05: sentinel من محرك قديم بلا إثبات + active: متابعة نفس PID بلا إرسال جديد؛ بلا cooldown خاطئ.
- S06: الاشتباه أثناء polling يمر إلى قرار المراقبة بدل break قبل activity gate.
- S07: انتهاء فعلي لرد يذكر التسعير: COMPLETED من دليل النهاية الصحيح، لا من النص وحده.
- S08: انتهاء المهلة مع نص جزئي ودون إثبات نهاية: حالة غير ناجحة، لا fallback COMPLETED ولا دوران حسابات.
- S09: فشل شبكة عابر ثم تعافٍ؛ وعدم تعافٍ حتى المهلة؛ لا حلقة لانهائية.
- S10: إلغاء أثناء SSE أو الانتظار أو fetch: لا send أو rotate لاحق، وتحرير الموارد.
- S11: P18 stop/final fetch لا يُتجاوز، والإثبات المهيكل في الرد النهائي لا يُترك تحت COMPLETED.

### التكامل والثوابت

- I01: credit بعد compact أو bypass يحفظ cloud checkpoint checksum ويتابع الحساب التالي.
- I02: effective fast mode يمنع archive/snapshot/diff/artifact scan/upload؛ لا تغيير لمسار GitHub المفعّل السابق.
- I03: boundaries للمدة 0 و179.999 و180 و180.001 و300 كما هي.
- I04: preview/cancel keyboard وlive rebind وTelegram handlers/offset/shutdown بلا regression.
- I05: لا جلسة/مشروع جديد بلا داعٍ، ولا تسريب cfg من محاولة إلى التالية.
- I06: مداخل module/direct-file/monolith تصل إلى main؛ غياب التوكن المتوقع ليس تجربة تشغيل حي ناجحة.

هذه حالات قبول، وليست وعدًا بعدد اختبارات نهائي؛ يمكن parameterization. لا تُحسب الحالات المكتوبة هنا كاختبارات منفذة.

## 6. خطوات الـchunks والحفظ ضد resets

1. لكل chunk: نطاق ضيق وهدف اختبار واضح. بعد تعديل ملف المصدر يُحفظ commit فورًا؛ يُرفع ويُحدّث PR قبل الانتقال إلى ملف مستقل.
2. تغييرات الجسر تستلزم تحديث حدود المولد وإعادة التوليد كمتابعة مترابطة قبل اعتبار chunk صالحًا للتشغيل. checkpoint وسيط غير متكامل يبقى draft وموسومًا بوضوح؛ لا إعلان parity أخضر قبل التوليد.
3. اختبارات reproducer المتوقعة الفشل تُوسم RED داخل checkpoint، ولا تُسجّل كتاسك إصلاح مكتمل. الدمج ممنوع حتى الأخضر الكامل.
4. سجل genspark يحتفظ بـ task ID، آخر commit مدفوع، آخر اختبار ونتيجته، الملفات المتبقية، والخطوة التالية بدقة؛ لا أسرار ولا HAR خام.
5. بعد reset: `pwd`، `git status`، `git fetch`، فحص PR والـremote head ثم استعادة المدفوع. لا إعادة خطوة بناءً على ذاكرة قديمة.
6. قبل كل push: مزامنة main، حل التعارضات مع احترام تغييرات المالك، وإعادة اختبار ما تأثر. لا squash يعبر merge base أو يمس commits المالك.
7. عند التسليم: تجميع commits الخاصة بالمهمة فقط في commit واضح، `--force-with-lease` إذا لزم، تحديث PR وتأكيد SHA بعيد وشجرة نظيفة.
8. PR #5 يبقى خطة/مراجعة. بعد GO يُحسم مع المالك تحويله لتنفيذ أو إنشاء PR تنفيذ جديد من main؛ لا إدخال تشغيل مفاجئ داخل PR وثائق مدموج أو غير معتمد.

## 8. التجربة الحية والرجوع

التجربة لا تستخدم أسرار HAR ولا تنفذ أثناء إعداد الخطة. بعد موافقة المالك تُنفذ على مشروع تجريبي وبأقل طلبات لازمة:

1. compact ثم برومبت بسيط: إثبات النهاية وreadback وpayload التالي.
2. استئناف حالة مؤجلة قديمة عبر بيئة اختبار آمنة دون العبث بمانفيست مشروع إنتاج.
3. رد يحتوي رابط تسعير ثم متابعة نصه حتى نهاية حقيقية.
4. المعاينة والإلغاء أثناء الانتظار والتوليد.
5. انتقال رصيد حقيقي إن أمكن طبيعيًا؛ لا استنزاف حساب عمدًا. عند عدم اختباره حيًا يُذكر صراحة ويظل اختبار التكامل هو المتاح.

معايير إيقاف التجربة: إرسال مكرر، مشروع/جلسة خاطئان، تداخل توليد، تدوير بلا إثبات، فقد الإلغاء، تنزيل ملفات في fast mode، أو اكتمال زائف.

الرجوع يكون إلى revision معلوم للجسر والمحرك والتوليد معًا، مع حفظ metadata السليمة وعدم حذف تاريخ المستخدم. الرجوع إلى النسخة القديمة قد يعيد COMPACT_BLOCKED؛ لذلك ليس حلًا للحادثة، وتُوقف التجربة/الأتمتة المتأثرة لحين قرار المالك. لا تنظيف يدوي جماعي للمانفيست ولا نشر تلقائي أثناء المراجعة.

## 9. تعريف الاكتمال وقرار الاعتماد

تُعتبر المهمة البرمجية مكتملة عندما تمر T01–T10، تُرفع كل التغييرات ويُوثق نطاقها، وتبقى حدود T11 معلنة إذا لم تُنفذ. الاعتماد الإنتاجي يحتاج تجربة T11 وموافقة التسليم T12، وليس فقط نجاح build.

قرار GO المطلوب يشمل صراحة: إصلاح المحرك والجسر، إضافة metadata مرتبطة بالطلب، إزالة قطع البث بالنص وحده، تصحيح deferred readiness مع بقاء الأمان، اختبارات وتوليد أمين. **لا يشمل GO تلقائيًا نشرًا حيًا أو دمجًا أو تغيير P18 أو العتبة أو تنزيل ملفات.**
