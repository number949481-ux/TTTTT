## 🔬 2. التشخيص الجنائي لعيوب Contents REST API القديم (Why v5.4?)

كان النظام يعتمد على حلقة تكرارية (`for file in upload_files`) تستدعي إندبوينت المحتويات:
1. **استنزاف مهول للكوتا والشبكة (2N Requests):**
   - لكل ملف يتم إرسال طلب `GET /contents/{path}` للتأكد من الـ SHA، ثم `PUT /contents/{path}` لرفع الملف.
   - مشروع من 100 ملف يتطلب **200 استدعاء شبكي**، مما يسبب بطئاً شديداً وإنهاكاً لحدود الـ Rate Limit.
2. **تشتت الهيستوري (Polluted Git History):**
   - كل ملف يترفع ينشئ **كوميت منفصل** في تاريخ الفرع؛ فرفع مشروع واحد يملأ سجل Git بـ 100 إلى 200 كوميت بدلاً من كوميت واحد يمثل حالة التشيك بوينت.
3. **فشل الريبو الفارغ بـ 404/422:**
   - التوثيق الرسمي لجيت هاب ينص حرفياً:
     > *"You are unable to create new references for empty repositories, even if the commit SHA-1 hash used exists. Empty repositories are repositories without branches."*
   - المحاولات السابقة للرفع على ريبو فارغ بـ `POST /git/refs` كانت تفشل حتماً.
4. **خطر الحالة الجزئية المبتورة (Inconsistent State):**
   - لو انقطع الاتصال عند الملف رقم 50، يتبقى 50 ملفاً مرفوعة على الفرع والـ 50 الأخرى غير مرفوعة، مما يكسر المشروع تماماً.

## 🛠️ 3. الحل المعماري الشامل في محرك `gh_bulk.py` (v5.4 Invariants)

تم بناء محرك `gh_bulk.py` مستقلاً بالكامل ليحقق المبادئ الهندسية التالية:

### 1️⃣ الكوميت الذري الواحد (Atomic Single Commit)
يتم مسح الملفات، وبناء شجرة Git Data API واحدة (`POST /repos/{owner}/{repo}/git/trees`) تضم كافة الملفات، ثم إنشاء كوميت واحد فقط (`POST /repos/{owner}/{repo}/git/commits`)، ثم تحديث مرجع الفرع (`PATCH /repos/{owner}/{repo}/git/refs/heads/{branch}`).
- إما أن يُدفع المشروع كاملاً في ثانية واحدة بـ Commit واحد نظيف.
- أو يفشل قبل تحديث المرجع ويبقى المستودع سليماً دون أي ملفات مكسورة.

### 2️⃣ تضمين المحتوى المباشر (Inline Content Optimization)
- استغلال توثيق Git Data API الرسمي: الملفات النصية ذات الحجم الصغير ($\le 4096$ بايت) يتم إرسال محتواها UTF-8 مباشرة في الـ Tree Node عبر خاصية `"content": "..."`.
- **التوفير:** تم الاستغناء عن استدعاءات `POST /git/blobs` لأكثر من 50% من ملفات المشروع، مما ضاعف السرعة وخفّض استهلاك الكوتا للنصف.

### 3️⃣ تهيئة المستودع الفارغ الذكية (Smart Bootstrap)
- قبل البدء، يفحص المحرك فروع المستودع `GET /branches`:
  - إذا كانت الفروع صفراً (`len(branches) == 0`) ➔ المستودع فارغ تماماً.
  - يقوم المحرك بالبحث في الأرشيف عن **أصغر ملف نصي حقيقي من المشروع** (مثل `index.html` أو `main.py`).
  - ينفّذ `PUT /contents/{path}` لمرة واحدة فقط لإنشاء الكوميت الافتتاحي وتأسيس الفرع الافتراضي.
  - بعدها مباشرة يكمل المزامنة الذرية فوقه دون أي ملف دخيل ودون أي تكرار.

### 4️⃣ التمييز بين الريبو الفارغ والفرع الجديد
- لو المستودع يحتوي على فروع قائمة، ولكن الفرع المطلوب (`branch`) غير موجود:
  - المحرك **لا يقوم بـ Bootstrap إطلاقاً**.
  - يستند إلى الفرع الافتراضي (مثل `main`) كـ Base، وينشئ الفرع بـ `POST /git/refs`.

### 5️⃣ الصمود التام عند انقطاع الاتصال (Resilient PATCH & Idempotency)
- لو حدث `ReadTimeout` أو انقطاع شبكة أثناء طلب تحديث الفرع `PATCH`:
  - المحرك لا يرمي خطأ عميانياً؛ بل يعيد قراءة مرجع الفرع `GET /git/refs/heads/{branch}`.
  - إذا وجد أن الكوميت نزل بنجاح ➔ يعلن **Idempotent Success** دون أي تكرار.
  - إذا وجد اختلافاً، يقارن الكوميتات عبر `compare_commits` للتأكد هل تم دمجه (Superseded) أو حدث تعارض حقيقي (409 Conflict) أو فشل تحقق (422 Validation).

### 6️⃣ سقف زمني إجمالي (Timeout Guard)
- تفعيل `MAX_TOTAL_SYNC_SECONDS = 120` لضمان عدم تعليق العملية مهما تكررت محاولات الـ retry التصاعدية.
