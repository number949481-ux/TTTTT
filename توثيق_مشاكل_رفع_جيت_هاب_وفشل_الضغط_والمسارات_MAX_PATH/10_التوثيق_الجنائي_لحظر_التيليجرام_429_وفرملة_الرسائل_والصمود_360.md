## 🔬 2. التشخيص الجنائي والسبب الجذري للأزمة (Root Cause & 5 Whys Analysis)

### أ. العَرَض المرئي (Symptom):
* تجمد واجهة بوت التيليجرام وتوقفه التام عن الاستجابة لأوامر المستخدم أو إظهار مراحل المعالجة الحية.
* ظهور رسائل خطأ في لوجات شبكة التيليجرام:  
  `HTTP 429 Too Many Requests: retry after 20`

### ب. شجرة التحقيق الجنائي خماسية الأسباب (The 5 Whys):
1. **لماذا علّق البوت واختنقت الاستجابة؟**  
   لأن خوادم Telegram Bot API حظرت التوكن مؤقتاً ورفضت استقبال أو معالجة أي طلبات جديدة منه.
2. **لماذا فرضت خوادم التيليجرام حظر الـ HTTP 429؟**  
   لأن البوت أرسل طوفاناً من طلبات التعديل الحية (`editMessageText`) المتتالية على نفس الـ `message_id` في نافذة زمنية ضيقة جداً (أقل من نصف ثانية بين الطلب والآخر).
3. **لماذا أرسل البوت طلبات تعديل متتالية بهذه السرعة الجنونية؟**  
   لأن خط أنابيب الحسابات (Account Pool) مر على عدة حسابات متتالية رصيدها منتهٍ أو صفر، وكانت كل دورة استبعاد حساب (`attempt-started` متبوعة بـ `attempt-failed`) تستغرق 0.2 ثانية فقط، وكان كود `AccountSelectionLiveTransport.publish` يستدعي `edit_telegram_message_text` مع كل حدث بلا أي فرملة أو تأخير زمني.
4. **لماذا لم يتعافَ البوت ذاتياً وينتظر انتهاء مدة الحظر؟**  
   لأن دالة النقل `_call_telegram_api_json` كانت تعتبر كود `429` خطأً عادياً وتعيد `ok: False` فوراً دون قراءة باراميتر `parameters.retry_after` القادم من استجابة تيليجرام، مما جعل حلقة المعالجة تُعيد المحاولة وتصطدم بنفس الحظر أو تدخل في حالة صمت مطبق.
5. **السبب الجذري النهائي (Root Cause):**  
   **غياب صمام فرملة زمني (Throttling Window)** للأحداث اللحظية السريعة في طبقة العرض الحي (`AccountSelectionLiveTransport`)، **وانعدام صمام ارتداد تلقائي (Auto-Backoff Retry)** يحترم توجيهات الـ 429 في طبقة النقل (`_call_telegram_api_json`).

## 🛠️ 3. المعمارية الهندسية الشاملة للحل (The 4 Architectural Invariants)

بناءً على التوجيهات الدقيقة للبشمهندس، تم تأسيس 4 ركائز معمارية فولاذية:

```
                  ┌─────────────────────────────────────────┐
                  │       حدث جديد من خط الحسابات         │
                  └────────────────────┬────────────────────┘
                                       │
                                       ▼
                     ┌───────────────────────────────────┐
                     │  هل الحدث أولوية قصوى؟            │
                     │  (account-claimed / handoff)      │
                     └───────┬───────────────────┬───────┘
                        نعم  │                   │ لا
                             │                   ▼
                             │      ┌─────────────────────────────┐
                             │      │ هل انقضت 7 ثوانٍ كاملة؟     │
                             │      │ (now - last_publish >= 7.0) │
                             │      └──────┬───────────────┬──────┘
                             │         نعم │               │ لا
                             │             │               ▼
                             │             │      ┌──────────────────┐
                             │             │      │  فرملة وتخطي     │
                             │             │      │  إرسال التيليجرام│
                             │             │      └──────────────────┘
                             ▼             ▼
                     ┌───────────────────────────────────┐
                     │    إرسال التعديل editMessageText   │
                     └─────────────────┬─────────────────┘
                                       │
                         استلام 429   │  استلام 200 OK
                       ┌───────────────┴───────────────┐
                       ▼                               ▼
        ┌─────────────────────────────┐       ┌─────────────────┐
        │ استخراج retry_after         │       │ نجاح التعديل    │
        │ نوم (retry_after + 1.0)     │       │ وتحديث المؤقت   │
        │ إعادة المحاولة تلقائياً     │       └─────────────────┘
        └─────────────────────────────┘
```

1. **فرملة الـ 7 ثواني الذكية (`7.0s Throttling Window`):**  
   حفظ طابع زمني دقيق `self.last_publish_time`. أثناء التنقل السريع وتخطي الحسابات الفارغة، يتم إسقاط طلبات تعديل التيليجرام صامتاً إذا لم يمر 7.0 ثوانٍ كاملة على آخر تعديل ناجح، مع استمرار التيرمينال ولوجات السيرفر في العمل والتسجيل الحي بنسبة 100%.
2. **استثناء القبول الفوري (Priority Event Bypass):**  
   عند وصول حدث قبول حساب صالح (`account-claimed`) أو نجاح المحاولة (`attempt-succeeded`) أو جاهزية رابط الاستئناف (`continuation-handoff-ready`)، **تُكسر الفرملة الزمنية فورياً**، ويُرسل التعديل إلى تيليجرام في نفس اللحظة ليراها المستخدم دون تأخير ثانية واحدة.
3. **صمام التعافي التلقائي من 429 في طبقة النقل (Auto-Backoff & Retry):**  
   في دالة `_call_telegram_api_json`، عند استلام استجابة `HTTP 429`، يتم استخراج حقل `retry_after` الرسمي من كائن `parameters`، والانتظار بمقدار `retry_after + 1.0` ثانية أمان، ثم إعادة إرسال الطلب تلقائياً، مما يقضي على تجمد البوت.
4. **التطابق المعماري المزدوج (Dual Parity SSOT):**  
   تطبيق التعديلات الجراحية بالتوازي وبنفس المنطق في الملف الأحادي الأساسي `01.33_telegram_gen_bridge.py` وفي الحزمة المعيارية المقسمة `bridge_refactor/parts/p04_telegram_api.py`.
