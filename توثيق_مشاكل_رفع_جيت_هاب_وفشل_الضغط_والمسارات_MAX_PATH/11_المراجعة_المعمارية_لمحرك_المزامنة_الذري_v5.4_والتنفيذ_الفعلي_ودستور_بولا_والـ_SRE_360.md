### أ. كسر الشلل التحليلي (Paralysis by Analysis) وحسم جدل الإصدارات
خلال الجولات السابقة دار نقاش معماري محتدم بين إصدارات المواصفة (v5.2 و v5.3 و v5.4):
* **في v5.2:** اقترح البعض اشتراط وجود فرع صالح مسبقاً، واعتبر أن المستودع الفارغ (Empty Repo) حالة استثنائية يجب أن يتدخل فيها المستخدم يدوياً بالـ Git CLI لعمل كوميت أول، وهذا ينافي متطلبات تجربة المستخدم (UX) لأن مستخدم التيليجرام لا يملك بيئة Git محلية.
* **في v5.3:** ظهر مقترح محاولة إنشاء مرجع مباشرة بـ `POST /git/refs` وافتراض نجاحها، وهو ما كان ينجح في بيئات المحاكاة (Mock) المغلقة.
* **الحقيقة الصادمة وسقوط الـ Mock (v5.4 Ground Truth):**  
  عند مراجعة التوثيق الرسمي لـ GitHub Git Data API وجدنا النص القاطع:
  > *"You are unable to create new references for empty repositories, even if the commit SHA-1 hash used exists. Empty repositories are repositories without branches."*  
  وهذا أثبت بالدليل القطعي أن الـ Mock كان يخدعنا بقبول طلب ترفضه خوادم GitHub الحقيقية بـ 404/422. وهنا تجلت قاعدة **Test-Before-Talk** و **Zero-Pleasing**؛ حيث تم تصحيح الفرضية واعتماد v5.4.

## 🛡️ 3. الصمامات الأربعة الحاكمة في تنفيذ محرك v5.4 (The 4 Critical Invariants)

لتأمين المنظومة 360° ومنع أي انهيار ميداني، تم إدماج 4 صمامات هندسية دقيقة داخل `gh_bulk.py`:

| # | الصمام المعماري | التحدي والمخاطرة | المعالجة الهندسية والتحصين 360° |
|---|---|---|---|
| **1** | **التفريق بين الريبو الفارغ والفرع الجديد** | الخلط بين ريبو خالٍ من الفروع تماماً وبين ريبو نشط لكن الفرع المطلوب غير منشأ فيه. | فحص `GET /branches`؛ إذا كان الناتج صفراً (`len(branches) == 0`) يتم تفعيل مسار الـ Bootstrap. أما إذا كان المستودع يمتلك فروعاً (`main` أو غيره) والفرع المستهدف غير موجود، نعتمد على رأس الفرع الافتراضي وننشئ الفرع بـ `POST /git/refs` دون Bootstrap. |
| **2** | **الاستراتيجية التأسيسية الذكية (Smart Bootstrap)** | فشل الـ Bootstrap إذا لم يجد ملفاً مناسباً أو إذا كان الملف ضخماً جداً أو ثنائياً. | استراتيجية ثلاثية المستويات: 1) البحث عن الملفات المعيارية الخفيفة (`index.html`, `main.py`, `app.py`, `package.json`, `README.md`). 2) البحث عن أصغر ملف نصي UTF-8 بحجم $\le 64\text{KB}$. 3) Fallback تلقائي حصين ينشئ ملف `README.md` قياسي يحتوي اسم ووصف المشروع لضمان عدم توقف العملية أبداً. |
| **3** | **تصنيف وتطبيع أخطاء 409 و 422** | التعامل مع أي خطأ 409 أو 422 على أنه تعارض دفع متزامن (Concurrent Conflict) وطلب التدخل البشري. | التحقق الفوري التلقائي (Idempotency Check) بقراءة `GET /git/refs/heads/{branch}`: إذا كان الـ SHA يطابق نفس الكوميت المنشأ حديثاً تُعتبر العملية ناجحة تماماً (Idempotent Success). ويتم فحص علاقة الكوميتات عبر `compare_commits` للتأكد هل تم الدمج (Superseded) أم تعارض حقيقي يستوجب رفع خطأ صريح. |
| **4** | **الصمود ضد انقطاع الشبكة أثناء الـ PATCH** | حدوث `ReadTimeout` أو انقطاع مفاجئ أثناء طلب تحديث الفرع `PATCH /git/refs` مما يترك حالة العملية مجهولة. | بدلاً من الفشل الفوري، يقوم المحرك بإعادة قراءة مرجع الفرع `GET /git/refs/heads/{branch}` للتأكد هل استلم خادم GitHub الكوميت وحدث المرجع قبل انقطاع الاتصال أم لا، وتأكيد النجاح دون تكرار الكوميت. |
